# 反偷懶案例庫與防作弊審查手冊 (Anti-Cheating & Industrial Rigor)

**何時讀本文**：計畫涉及渲染、影音、重構、數值指標，或 Critic 需要判斷「這是不是表面工夫」時。

---

## 1. 核心質問

> 這就是開發者要的嗎？還是只是用表面工夫通過檢查？

Critic 針對每個提案確認：是否建立了可編輯、基於參照與動態欄位的底層架構，而不是用寫死的值讓畫面或測試看起來正確。

---

## 2. 經典表面工夫與防作弊案例庫

| 編號 | 作弊 / 表面工夫類型 | 典型作法 | Critic 判定依據 | 合格做法 |
| :-: | :--- | :--- | :--- | :--- |
| **C1** | **特徵百分比作弊**<br>(Percentage Illusion) | 宣稱「語意特徵覆蓋率 94.1%」，但私下將「不得」、「必須」、「嚴禁」等核心規範性約束整句刪除 | 執行 P2 句子級規範性語句比對 (`lost_clauses.json`) | 規範性語句遺失數必須為 0；任何刪除必須有 P7 使用者決策紀錄。 |
| **C2** | **未經證偽的全零盲區**<br>(The Blind Watchdog) | 稽核工具回報「全零儀表板」，但稽核規則寫得太寬鬆，連壞檔案都抓不到 | 是否具備 P1 變異植入測試 (Mutation Testing M1~M14) | 變異偵測率必須達 100%；乾淨基準誤報必須為 0。 |
| **C3** | **手寫對照報告灌水**<br>(Unverified Claims) | 手寫 DIFF_SUMMARY 宣稱「不含 Bash」，但實際檔案中依然宣告了 Bash | 是否具備 P3 腳本自動生成與 P4 獨立驗證 (`verify_report.py`) | 對照報告一律由工具自動生成，指標與事實陳述重現率達 100%。 |
| **C4** | **口頭程式強制**<br>(Unverified Enforcement) | 宣稱由程式碼硬守門，但若代理人直接呼叫原生 shell (`rm -rf`) 即可繞過 | 是否通過 P5 繞過滲透攻擊測試 (`enforcement_matrix.md`) | 必須經攻擊測試驗證；無法由 OS 底層攔截者必須誠實標註「權限層防禦」。 |
| **C5** | **硬編碼常數假冒動態** | 在 JSON 填入固定數字（如猜測的 ratio），假裝由演算法計算 | 欄位值是否可追溯到計算來源或參照時間軸 | 由時間軸或參照資料動態計算，並可被編輯。 |
| **C6** | **遮蔽假冒排版修復** | 疊加全域黑底色塊或遮罩，掩蓋組件內部文字破版 | 修復是否發生在組件內部版面邏輯 | 在組件內修正版面，並以完整畫面驗證。 |
| **C7** | **報表驗收假冒實體驗收** | 只檢查 Python 輸出或 JSON 欄位是否存在 | 是否產出未裁切之 1080p 實體影格 (Contact Sheet) | 抽取實體影格檢視原圖；驗證介面端到端貫通。 |

## 3. 跨模組泛用性與效能檢查

1. **靜態預檢與動態無頭採樣是否共用同一個合約核心？**
2. **是否把本次特定缺陷的處理寫死在單一模組內？**
3. **效能指標必須寫明量測方法與數學公式**：
   - 範例：對偶交換測試（Pairwise Swap Test）：
     $$\Delta = 	ext{Score}(	ext{Swapped Beat Order}) - 	ext{Score}(	ext{Original Timeline})$$
     門檻要求 $\Delta < -0.30$，數值越負代表原排定之聲畫必然性越強，拒絕無公式之孤立數字。
